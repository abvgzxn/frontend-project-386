# Календарь звонков

Учебный сервис записи на звонок по мотивам Cal.com. Разработка ведётся с помощью ИИ-агента: обсуждение → спецификация → тикеты → реализация → проверка.

## Сценарий владельца

1. Владелец открывает страницу управления календарём без авторизации. Владелец один и задан заранее.
2. Создаёт тип встречи: указывает название, описание и длительность, например «Знакомство», «Короткий вводный звонок», 30 минут.
3. Созданный тип появляется в публичном каталоге и становится доступен гостям.
4. После бронирования гостем владелец открывает список предстоящих встреч всех типов и видит новую запись с типом встречи, датой и временем начала и окончания.

## Сценарий гостя

1. Гость открывает публичный каталог без регистрации.
2. Выбирает тип встречи и видит его описание и длительность.
3. Открывает календарь записи на 14 календарных дней и выбирает день.
4. Выбирает свободное время. Длительность встречи соответствует выбранному типу.
5. Подтверждает бронирование и получает сообщение об успешной записи.
6. Запись появляется в списке предстоящих встреч владельца. Занятый интервал исключается из доступного времени для всех типов встреч.
7. Если время успел занять другой гость, сервис сообщает о конфликте и предлагает выбрать другой свободный слот.

Поля формы гостя будут определены в спецификации.

## Правила бронирования

- Окно записи содержит 14 календарных дней и сдвигается с течением времени.
- Запрещены любые пересечения встреч одного владельца, включая частичное наложение разных типов.
- Встреча может начинаться точно в момент окончания предыдущей.
- Проверка занятости и создание записи должны атомарно исключать конфликт при одновременных запросах. Если два запроса претендуют на пересекающиеся интервалы, успешным может быть только один.
- Бронирование за пределами окна записи и рабочего времени не допускается.
- Начальный день окна, часовой пояс, рабочие дни и часы, а также шаг доступных стартов будут зафиксированы в спецификации до реализации.

## Границы проекта

В проект не входят авторизация, личные кабинеты, внешние календари и уведомления.
Редактирование, удаление, отмена и перенос встреч не включены в текущий обязательный объём.

Хранение в памяти процесса допустимо. Если выбран этот вариант, перезапуск сбрасывает записи; это ограничение должно быть явно отражено в итоговом README. Способ хранения пока не выбран.

## API и сборка

- Исходный контракт API описывается в TypeSpec.
- Из контракта генерируется OpenAPI, из OpenAPI — клиентский SDK для фронтенда.
- До утверждения стека необходимо проверить наличие подходящего генератора SDK для языка фронтенда.
- Серверные типы и маршруты генерируются, если выбранный фреймворк поддерживает это. При отсутствии генератора сервер реализуется по контракту и проверяется тестами.
- Приложение должно собираться в Docker-образ и запускаться в контейнере.
- Итоговый сервис должен быть доступен по публичной ссылке.

## Статус

Сохранён черновик пользовательских сценариев по описанию задания и публичной странице Cal.com. Интерактивный сценарий в авторизованном Cal.com не проходился. Стек и правила расписания ещё не утверждены.

Референс: https://cal.com/

## Каркас стека

Проект использует TypeScript, React 19 + Vite 8 + Mantine 9 для фронтенда,
Fastify 5 для API, Vitest 5 для тестов и npm workspaces с одним корневым
`package-lock.json`. Контракт описывается в TypeSpec 1.18, затем генерируются
OpenAPI 3.1 и Fetch SDK через Hey API. Инструменты и задачи закреплены в
`mise.toml`, Git-хуки настроены через hk, CI находится в
`.github/workflows/ci.yml`.

На текущем шаге реализован только `GET /api/health` и страница, показывающая
статус API. Бизнес-функциональность из сценариев владельца и гостя намеренно
не реализована. Сервер хранит данные в памяти только как будущая опция; сейчас
данные бронирований отсутствуют. Docker и публичная публикация остаются
следующими этапами проекта.

Команды установки, запуска и проверок описаны в `CONTRIBUTING.md`.
